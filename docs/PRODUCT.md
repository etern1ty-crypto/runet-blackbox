# Product discovery: от сетевой метеосводки к dependency preflight

## Что было в архиве

Исходная версия — `runet-blackbox` 0.3.1. Это не web backend и не готовый SaaS. Реальный стек: JavaScript ESM, Node.js ≥22, стандартные `dns/net/tls/http/https/crypto/fs/child_process`, встроенный `node:test`, статические HTML/CSS/JS, JSON/JSONL и GitHub Actions/Pages. Прямых и транзитивных npm-зависимостей в lockfile нет.

Основная исходная задача: пользователь измеряет доступность публичного домена из своей сети, получает диагноз по слоям и добровольно передаёт очищенный отчёт через GitHub Issue. Импортёр и агрегатор создают общественную «сетевую метеосводку».

Уже существовали CLI, packs, сравнение DNS, детектор VPN-подобных интерфейсов, схема отчёта, sanitizer, diagnosis engine, GitHub importer, dashboard, SVG-карточки и weekly digest. Скрытая продуктовая ценность — не карта блокировок, а **переносимый диагностический артефакт из конкретной сети** и готовый механизм exit code, который можно превратить в CI gate.

## Три жизнеспособных направления

| Сценарий | Пользователь / покупатель | Ценность | Основное ограничение | Монетизация-гипотеза |
| --- | --- | --- | --- | --- |
| **1. B2B dev-tool: preflight публичных зависимостей** | Platform/SRE/DevEx, команды с self-hosted CI и распределённой разработкой | Быстро отделить сетевую причину неудачной сборки от проблемы приложения; приложить одинаковый отчёт к тикету | Не заменяет download/auth/E2E тесты; требуется калибровка ожидаемых кодов | Платное внедрение, поддержка конфигов, позднее private control plane |
| **2. Support kit для MSP и IT-support** | Службы поддержки, аутсорсинговые IT-команды | Один безопасный сборщик вместо просьбы прислать пять несогласованных команд и сырые логи | У пользователя должен быть Node; свободные подписи надо проверять | Пакеты интеграций с тикетами и сопровождение |
| **3. Community network weather** | Волонтёры, исследовательские сообщества | Сравнимые публичные сигналы по сетям | Нет устойчивого покупателя, сильные Sybil/privacy риски, требуется независимость измерений | Гранты, спонсорство, исследовательские услуги |

Это качественное сравнение по существующему коду, а не измеренный рыночный рейтинг. Изучение конкурентов подтверждает существование категории, **но не подтверждает PMF именно этого проекта**.

## Выбор №1

**Локальный preflight доступа к публичной developer infrastructure из CI-runner’ов и сетей команды.**

Первый пользователь — инженер платформы, который регулярно разбирает «npm install завис», «GitHub недоступен только из офиса» или «у клиента ошибка, а наш uptime зелёный». Покупатель — руководитель engineering/platform, которому важно сократить время первичного разбора и число ручных эскалаций.

Важная оговорка: новая версия проверяет front door сервиса (HTTPS origin root), а не сам `npm install`. Она помогает сузить причину, но успешный preflight не гарантирует успешную загрузку артефакта.

### Где преимущество, а где его нет

- **Перед разрозненными curl/dig/openssl-командами:** единый формат, единый проверенный адрес, ограниченные ресурсы, повторяемый сценарий и CI-артефакты. Это непосредственно реализовано.
- **Перед внедрением отдельной платформы ради одного тикета:** отсутствие аккаунта, сервера, агента-демона и runtime-пакетов. Это преимущество в низком пороге входа, не в функциональной полноте.
- **Не «лучше Prometheus» в мониторинге.** Blackbox Exporter уже поддерживает HTTP(S), DNS, TCP и другие probes. Когда Prometheus уже развёрнут и нужен непрерывный мониторинг, exporter часто предпочтительнее.
- **Не «лучше Checkly» в browser/API synthetics.** Checkly имеет monitoring-as-code, private locations и CI-интеграции. Здесь ставка на маленький локальный triage-инструмент без control plane.
- **Не «замена OONI».** Исследовательская атрибуция вмешательства требует другой методологии, контрольных измерений и осторожного обращения с данными.

### Первое предложение покупателю

«За один короткий пилот внедрим одинаковую диагностику публичных зависимостей в ваши runner’ы и support runbook. Не передаём сырые данные внешнему вендору. Результат пилота — воспроизводимые отчёты и измеренное время triage».

Начать с оплачиваемого внедрения, а не строить биллинг и мультиарендность без клиентов. Возможный тест цены: фиксированный пилот и последующее сопровождение за отдельную плату; конкретный прайс формировать после интервью и оценки объёма. Никаких вымышленных ARR, размера рынка, ROI или заявленных клиентов.

## Проверка PMF, а не его декларация

1. Провести интервью с инженерами, у которых уже были сетевые сбои сборок. Попросить разобрать последний реальный инцидент.
2. Установить инструмент в нескольких согласованных сетях/runner’ах; зафиксировать baseline поддержки без инструмента.
3. Собирать длительность первичного разбора, долю понятных отчётов, ложные тревоги и фактические действия после диагностики. Не превращать количество отчётов в KPI ценности.
4. Попросить оплатить следующий период сопровождения. Повторное использование и готовность платить сильнее количества звёзд GitHub.
5. Только после повторяемой пользы проектировать private control plane, сбор fleet-снимков, RBAC и интеграции с инцидентами.

## Что реализовано для выбранной ниши

`preflight`, небольшой pack `ci`, конфиг с per-target HTTP expectations, ограниченный worker pool, JSON/JUnit/Prometheus, атомарные snapshot-файлы, graceful shutdown, безопасный путь probes и непротиворечивая агрегация. Внешние сервисы не вызываются ради телеметрии, аккаунты и токены не требуются.
